- Title: Enable supervised trading runtime

## Goal

Safely re-enable momo-trading runtime from read-only mode with preflight checks, monitoring, and documented follow-up plan

## Scope

In scope:

- Runtime preflight checks before enabling automated trading.
- Protected runtime settings change from read-only/semi-auto to full autonomous trading.
- Live monitoring of activities, trades, pending orders, broker/DB reconciliation, lifecycle integrity, and account snapshot freshness.
- Safety fallback to read-only/semi-auto and scheduler stop when integrity temporarily reported `FAIL`.
- Documented follow-up plan for supervised re-enable.

Out of scope:

- Unrelated trading behavior changes.
- DB reset, migration, deploy, broker-affecting command unless separately approved.

## Constraints

- Preserve unrelated dirty worktree changes.
- Keep broker and runtime safety boundaries explicit.

## Research Gate

Sources checked:

- SEC Rule 15c3-5 market access risk management controls: https://www.sec.gov/rules-regulations/2011/06/risk-management-controls-brokers-or-dealers-market-access
- FINRA Regulatory Notice 15-09 algorithmic trading supervision/control practices: https://www.finra.org/industry/notices/15-09
- Kiwoom OpenAPI+ developer guide for `SendOrder` and order types: https://download.kiwoom.com/web/openapi/kiwoom_openapi_plus_devguide_ver_1.1.pdf

Plan implications:

- Adopt: automated trading may run only with pre-trade limits, order confirmation, reconciliation checks, and an operator-visible stop condition.
- Adopt: any integrity `FAIL` during live operation triggers a safe fallback before further automated orders.
- Defer: code changes to reduce transient pending-confirm false positives until the runtime state is stable and reviewed separately.
- Reject: continuing autonomous order submission while broker/DB lifecycle integrity is failing.

## Completion Criteria

- Runtime was enabled from read-only and observed through at least one live cycle.
- Orders/trades generated by the cycle were checked through admin APIs.
- Any integrity issue was handled with a safety fallback.
- Focused runtime verification was run and final state was documented.
- Remaining risks and re-enable plan are documented.
